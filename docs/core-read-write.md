# Read ↔ write: how close is the reader's Thunder Text to Thunder Core?

> Generated by `node compiler/scripts/core-read-write.mjs`. Do not edit by hand; run the script again.

Thunder's rule is that **reading and writing are the same language**: the Thunder Text the reader prints for a
function should be Thunder Core a person can edit and compile back. This page measures how far we are, on 20
small Python functions, so the next step (moving the reader's output toward Core) has a concrete list.

## Results

| Measure | Result |
| --- | --- |
| Reader's text compiles as Core, unchanged (whole function) | **0 of 20** |
| Reader's step lines that parse as a Core statement (bullet and "(line N)" removed) | **1 of 66** (2%) |
| The same step lines after 8 mechanical rewrites (verb forms and ":" only, listed below) | **36 of 66** (55%) |
| Hand-written Core versions that compile | **20 of 20** |

No reader output compiles as Core today. That is expected: the reader was built to *describe* code (third
person, "Sets total to 0", "Gives back 0"), and Core is written as instructions ("Set total to 0", "Give 0").
The gap is mostly mechanical, listed below by how often each shape appears.

## Gap list (reader line shapes that do not parse as Core)

| Reader shape | Lines | Example | What Core writes | How the reader converges |
| --- | --- | --- | --- | --- |
| Ask: | 16 | `Ask: Member and total is at least 100?` | `When <condition>:` … `Otherwise:` | Print a question as `When …:` with the Yes branch indented under it and the No branch as `Otherwise:`; keep "Ask" only in the picture. |
| Gives back | 15 | `Gives back 0` | `Give <value>` | Print "Give"; Core also accepts "Give back". |
| Answer: | 9 | `Answer: Yes` | `Give <value>` | In a rule card, an answer is what the function gives back: print `Give "A"`, `Give 15`, `Give yes`. |
| Writes a log or message | 6 | `Writes a log or message — calls: print("Hello, {name}!")` | `say <value>` | A print/log call becomes `say "…"` with `{name}` holes (already the reader's text style). |
| code shown as code (`…` (code, not explained)) | 5 | `return total * 0.2 (code, not explained) — means: return total * 0.2` | the expression itself | Expressions the reader shows as code (`return total * 0.2`) need the No-loss meaning model to print as Core expressions (`Give total * 0.2`). |
| Repeats | 4 | `Repeats: for i in range(1, n + 1): (code, not explained)` | `Repeat while <condition>:` | Imperative verb ("Repeat", not "Repeats") and a closing ":". |
| Sets | 3 | `Sets total to 0` | `Set <name> to <value>` | Imperative verb ("Set", not "Sets"). Same words otherwise. |
| Adds | 2 | `Adds o price to total` | `Increase <name> by <value>` / `Add <item> to <list>` | Print "Increase total by o price" for numbers and "Add … to …" for lists; possessives become `o's price`. |
| For each | 1 | `For each o in orders` | `For each <item> in <list>:` | Add the closing ":" and drop the separate "For each:" line; a `range(...)` loop becomes `For each i from 1 to n:`. |
| Stores | 1 | `Stores the word entry in counts under word in counts — value: counts.g` | `Set <map> at <key> to <value>` | Print `Set counts at word to (counts at word otherwise 0) + 1`; needs the meaning model for `.get(k, 0)` (shown as code today). |
| Tries | 1 | `Tries the next steps and handles the errors named below` | the protected statement, then `If this fails:` | Core attaches `If this fails:` to the statement before it; the reader should print the protected steps, then `If this fails:` (a block of several steps needs a Core `Try:` block, planned). |
| Stop: | 1 | `Stop: ValueError: "Insufficient funds"` | `Stop with "<message>"` | Print `Stop with "Insufficient funds"`; the error kind stays in Details. |
| Subtracts | 1 | `Subtracts 1 from n` | `Decrease <name> by <value>` | Print "Decrease n by 1". |

The mechanical rewrites measured above: 

- `Sets (.+?) to (.+)` → `Set $1 to $2`
- `Gives back (.+)` → `Give $1`
- `Answer: (.+)` → `Give $1`
- `Repeats while (.+)` → `Repeat while $1:`
- `For each (.+?) in (.+)` → `For each $1 in $2:`
- `Subtracts (.+?) from (.+)` → `Decrease $2 by $1`
- `Adds (.+?) to (.+)` → `Increase $2 by $1`
- `Ask: (.+)\?` → `When $1:`

Lines that still fail after them need the reader to print values as Core expressions (possessives such as `o's price`, code shown as code, and "Writes a log or message — calls: print(…)").

Other differences that are not single lines:

- **The title line.** The reader prints `Calculate discount` and `You give it: total, member`; Core writes `To calculate discount:` and `Receive total and member`.
- **Yes/no function names.** Python `is_adult` reads as "Is adult?". "is" is a Thunder word, so Core v0 cannot use it in a name (the Core versions say `check adult`). Next: a `To decide whether <name>:` form that makes a yes/no function, matching the reader's question title.
- **Truthiness.** Python `if member:` reads as "Member?"; Core asks for `member is true`, because "truthy" differs between languages. The reader should print the explicit comparison when it knows the value is yes/no.
- **Possessives.** The reader prints `o price`; Core writes `o's price` (the reader already uses 's in some places).
- **Line numbers.** `(line N)` is a link to the original code; Core files have their own lines. Thunder Text keeps them as trailing comments (`# line 4`) once the reader prints Core.
